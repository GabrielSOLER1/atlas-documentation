# Atlas Documentation

Internal documentation for Atlas Conseil, built with **Symfony 7.4, Vue 3, PostgreSQL 17 and Docker Compose**.

The application uses no external API, analytics service, CDN, remote font or email service. Assets and activity data stay on the internal infrastructure.

## Quick start

### 1. Requirements

Install Git, Docker with Docker Compose v2 and OpenSSL. Start Docker, then clone the private repository using a GitHub account that has access:

```sh
git clone https://github.com/GabrielSOLER1/atlas-documentation.git
cd atlas-documentation
```

If you already have the project folder, enter it directly. The repository root should contain `compose.yaml` and `scripts/start.sh`.

The initial image build downloads dependencies on the build workstation. For an isolated server, use the offline installation below.

### 2. Start Atlas

```sh
sh scripts/start.sh
```

This creates missing local secrets and TLS certificates, builds the application, starts PostgreSQL and waits for both services to be healthy. An existing `.env` and database are preserved.

### 3. Trust the internal certificate

Import **`certs/ca.crt`** into the trusted certificate-authority store of each client device/browser. This enables certificate validation without a browser warning. Do not disable certificate checks.

Only distribute `ca.crt`. Keep `ca.key`, `server.key` and `.env` private. The certificate covers `localhost`, `127.0.0.1` and `atlas.u5`.

### 4. Open and sign in

Open [https://localhost:8443](https://localhost:8443).

On a fresh installation, a **single administrator** is created from these settings in `.env`:

- `BOOTSTRAP_ADMIN_EMAIL`
- `BOOTSTRAP_ADMIN_NAME`
- `BOOTSTRAP_ADMIN_PASSWORD` — randomly generated by the start script

Open the local `.env` file in your editor to read these credentials. Each clone generates its own secrets, certificates and administrator password. Accounts and documents from another installation are not transferred by Git; use a protected database export when deliberately migrating them.

Existing installations keep their current accounts and passwords. Bootstrap settings do not reset them. There is no public registration endpoint or sign-up form.

When the server operator renews existing local credentials, an optional private `.env.credentials` file may hold the current access details. It is excluded from Git and Docker builds. It is not created or transferred by a clone; a fresh installation uses its own root `.env`.

### 5. Create accounts and documentation

As an administrator:

- **Comptes & accès:** create an account, choose its role, deactivate or reactivate it.
- **Créer une documentation:** set its title, category and summary; add steps, notes, checklists or code blocks; reorder blocks and preview before publishing.
- **Journal d’activité:** inspect successful logins, failed attempts and administrative actions. Period and event filters are available.

Users can read, search and browse guides by category. Help and privacy pages explain access and personal-data processing. The interface is in French.

## Personal workspace and administrator roadmap

Click the account name in the header to open **Mon profil**. Each member can edit their display name, optional function, department and short introduction, choose an initials colour and increase guide text size. Pending changes prompt before leaving the page.

Profile photos accept JPEG, PNG or WebP up to 256 KB. The server checks image dimensions, crops a 256 × 256 square, re-encodes it as WebP and strips source metadata. Photos stay in PostgreSQL and are served only to their signed-in owner. You can remove your photo from the profile page.

Use the bookmark button to keep guides in **Mes favoris**. Favorites are private to each account. The library supports recent-update and alphabetical sorting; code examples have a copy button and guides have a print layout.

The **Roadmap administrateur** is one interactive guide with twelve connected steps. Click a node to read its checklist and open the corresponding internal action. Progress is personal and stored with the administrator account. Both the page and API require an administrator role. Its content is maintained in `backend/database/roadmap.json`.

The initial library includes ten guides about internal access, assistance, workstations, shared files, session security, printing, meeting rooms, suspicious messages, file recovery and handover. Startup adds missing built-in guides without overwriting existing documents.

## Upgrading an existing installation

Back up the database before updating. On startup, schema changes and recorded data migrations run transactionally. The domain migration replaces the previous internal domain with `atlas.u5`, converts the original administrator account to **`admin@atlas.u5`**, and sets its display name to **admin**. Existing passwords and unrelated account addresses are preserved. Previous sessions may require a new login.

Update your local `.env` and any private credential file to use the new account addresses. These files are intentionally outside Git. Point internal DNS and the HTTPS proxy to **atlas.u5**. The certificate script automatically reissues an old-domain server certificate using the existing internal CA; clients that already trust that CA do not need a different authority.

The default Compose project is now `atlas-documentation`. Existing users of a differently named Compose project must deliberately migrate their database export into the new project, or continue temporarily with their previous `COMPOSE_PROJECT_NAME`. Changing the Compose name alone creates a different database volume. Do not remove the old volume before checking the restored data. See the recovery guide.

## Internal deployment

Relevant `.env` settings:

| Setting | Default / purpose |
| --- | --- |
| `APP_PUBLIC_URL` | `https://localhost:8443`; use `https://atlas.u5` behind the internal reverse proxy |
| `APP_PORT` | `8080`, HTTP redirect only |
| `APP_HTTPS_PORT` | `8443`, application HTTPS port |
| `APP_ENFORCE_HTTPS` | `1`; keep enabled on the deployed portal |
| `APP_SECRET` | Private Symfony secret |
| `DB_PASSWORD` | Private PostgreSQL password |

Both published ports bind to **127.0.0.1**. PostgreSQL has no published port and uses an isolated internal network. The application ingress network disables IP masquerading, and no external DNS resolver is configured for the application.

For VM3 access, configure internal DNS and a reverse proxy on **VM1's private LAN address**. Forward all paths to `https://localhost:8443`, including `/api` and `/build`, and validate the upstream certificate against `certs/ca.crt`. Use a trusted internal certificate for the proxy's `atlas.u5` endpoint as well. Do not publish the service on an Internet-facing interface.

See [the architecture report](docs/RAPPORT_ARCHITECTURE.md) and [internal integration notes](docs/INTERNAL_DEPLOYMENT.md).

## Offline installation

On the build workstation, prepare the images once:

```sh
sh scripts/start.sh
docker save -o atlas-images.tar atlas-documentation-app:latest postgres:17-alpine
```

Transfer the project and image archive through your internal transfer method. On the target server:

```sh
docker load -i atlas-images.tar
sh scripts/start.sh --offline
```

Offline mode does not build or pull images. Missing secrets and certificates are generated locally. Do not copy another installation's `.env` unless deliberately restoring that installation.

## Operations

| Action | Command |
| --- | --- |
| Check health | `docker compose ps` |
| View technical logs | `docker compose logs --tail=80 app` |
| Stop | `docker compose stop` |
| Start | `docker compose start` |
| Rebuild after changes | `sh scripts/start.sh` |
| Check application and database over TLS | `curl --cacert certs/ca.crt https://localhost:8443/api/health` |

Application events are stored in PostgreSQL and purged after 30 days when the journal is accessed or a new event is recorded. Technical Docker logs rotate at 10 MB, keeping three files per service.

A role change invalidates existing sessions. Deactivation blocks the next authenticated request. Sessions expire after 30 minutes of inactivity. Five failed attempts for the same identifier and network address block further attempts for 15 minutes.

### Reset an account password

Run this command on the server, substituting the account email if needed:

```sh
docker compose exec --user www-data app php bin/console app:reset-password admin@atlas.u5
```

Enter and confirm a new password when prompted; input is hidden. Existing sessions become invalid after the password change. This command does not create a public password-reset endpoint.

## Backup and recovery

```sh
sh scripts/export-db.sh
sh scripts/restore-test.sh backups/ACTUAL_EXPORT_FILE.sql
```

The first command prints the generated SQL file path. Exports include accounts, structured guides and application events. Keep exports private and include them in the internal Restic backup.

The restore test uses a separate database, applies schema upgrades without creating missing content, and checks its data. It prints the command to serve that database on `https://localhost:8444`.

See [main database recovery](docs/RESTAURATION.md). Protect backups of `.env`, certificates and the private CA key separately; the SQL export does not contain these files.

## Validation

Run HTTP tests on a restored validation instance, using its HTTPS URL and the internal CA:

```sh
ATLAS_CA_FILE=certs/ca.crt python3 tests/smoke.py https://localhost:8444
ATLAS_CA_FILE=certs/ca.crt python3 tests/users.py https://localhost:8444
ATLAS_CA_FILE=certs/ca.crt python3 tests/internal.py https://localhost:8444
ATLAS_CA_FILE=certs/ca.crt python3 tests/profile.py https://localhost:8444
ATLAS_CA_FILE=certs/ca.crt python3 tests/roadmap.py https://localhost:8444
```

Set `ATLAS_ADMIN_EMAIL`, `ATLAS_ADMIN_PASSWORD`, `ATLAS_USER_EMAIL` and `ATLAS_USER_PASSWORD` in your local test environment before authenticated tests. There are no built-in account passwords. Create the ordinary user through an administrator before taking the validation export. Do not commit test credentials. `security.py` needs only `ATLAS_CA_FILE`, as it checks anonymous access.

The account and publishing tests create records; use a separate database. For main-server TLS, secure-cookie, header, redirect and 404 checks:

```sh
ATLAS_CA_FILE=certs/ca.crt python3 tests/security.py https://localhost:8443
```

[Verification results](docs/RESULTATS.md) and [manual checks](docs/TESTS.md) describe the checks performed.

## Code layout

```text
backend/src/Controller/       API endpoints and access checks
backend/src/Security/         Authentication and account refresh
backend/src/Service/          Database, document validation and local audit
backend/src/EventSubscriber/  HTTPS, headers, session expiry and errors
backend/database/            Schema and initial guides
frontend/src/views/          Portal, editor, accounts and information pages
frontend/src/components/     Local logo, icons and safe document rendering
frontend/public/             SVG logo and favicon
scripts/                     Startup, certificates, export and restore
```

Secrets stay in server-side environment settings. The browser uses a session cookie and CSRF tokens; no API key is needed. Documents are rendered as text and controlled block types, never as arbitrary HTML.
